# План навантажувального тестування (ЛР №4)

## 1. Об'єкт тестування

**Multidimensional Portal Generator API** — FastAPI-сервіс розрахунку викривлених траєкторій порталів.

| Компонент | Деталі |
|---|---|
| Запуск | `docker compose` → `db` (PostgreSQL 16), `backend` (`uvicorn src.main:app`, 1 воркер, порт 8000), `client` (Django, порт 8080, у тесті не бере участі) |
| Base URL | `http://localhost:8000` |
| Автентифікація | JWT Bearer (HS256, TTL 30 хв), паролі — bcrypt |
| Обчислення | `calculate_secure_coordinates` у `ProcessPoolExecutor`, O(N), N = max(8, complexity·8)+1 точок; результат зберігається як JSON у `portal_simulations` |

## 2. Інструмент

**Locust** (Python). Сценарії — це звичайний Python, тієї ж мови, що й сервіс: просто генерувати
реалістичні дані, працювати з JWT, валідувати тіло відповіді й групувати URL. JMeter — GUI/XML,
важкий у code review; k6 (JS) і Gatling (Scala/Kotlin) ефективніші як генератори, але вводять другу
мову. Для цільових сотень VUsers Locust достатньо; headless-режим дає CSV + HTML для звіту.

## 3. Цільові ендпоінти (MVP) і ваги

Перелік підтверджено за `src/main.py` та `GET /openapi.json`. Ендпоінтів читання списку/однієї
симуляції в API немає, тому «читання» представлене профілем користувача.

| # | Запит | Тип | Вага | Частка* | Обґрунтування |
|---|---|---|---:|---:|---|
| 1 | `GET /users/me` | read | 6 | ~43% | Найчастіша дія: кожне відкриття дашборда клієнта |
| 2 | `POST /simulations/run` (параметри траєкторії) | write + CPU | 4 | ~29% | Основна бізнес-операція |
| 3 | `POST /simulations/run` (масив `coordinates`) | write | 1 | ~7% | Альтернативна гілка того ж ендпоінта |
| 4 | `PUT /users/{id}` | write | 1 | ~7% | Рідкісне редагування профілю (тільки email, без bcrypt) |
| 5 | `POST /auth/login` | auth (CPU, bcrypt) | 1 | ~7% | Повторний вхід після закінчення токена |
| 6 | `GET /admin/dashboard` | read, RBAC | 1 | ~7% | Звичайний користувач має отримати **403** (рахується як успіх) |
| — | `POST /auth/register` + `POST /auth/login` | on_start | 1 раз/VU | — | Кожен VU створює свого користувача |

\* частка серед задач циклу, без on_start.

## 4. Тестові дані

- email: `lt-<uuid>@loadtest.example.com` — унікальний на кожного VU (БД може бути порожньою).
- `complexity`: 1–10 (70%), 11–50 (25%), 51–100 (5%) — переважно легкі, інколи важкі розрахунки.
- `dimension_id` 1–1000, `initial_speed` 0–5000, `object_mass` 0.1–10 000.
- `coordinates`: 3–60 випадкових чисел у [-10⁴, 10⁴].

## 5. Профіль навантаження

| Прогін | VUsers | Spawn rate | Тривалість | Мета |
|---|---:|---:|---:|---|
| smoke | 5 | 5/с | 30 с | Перевірка, що сценарій працює (0% помилок) |
| `run_10u` | 10 | 5/с | 3 хв | Базова лінія, низьке навантаження |
| **`run_50u`** | **50** | **5/с** | **5 хв** | **Основний (початковий) профіль** |
| `run_100u` | 100 | 5/с | 3 хв | Пошук точки перелому |
| `run_200u` | 200 | 5/с | 3 хв | Пошук точки перелому / помилок |

`wait_time = between(1, 3)` с. Конфігурація основного прогону — `locust.conf`.

## 6. Метрики та критерії

| Метрика | Джерело | Орієнтир для MVP |
|---|---|---|
| RPS | Locust `*_stats.csv`, `*_stats_history.csv` | росте ~лінійно з VUsers |
| Латентність avg / min / max / median / p95 / p99 | Locust | p95 легких ендпоінтів < 500 мс, `/simulations/run` < 1000 мс |
| Error rate | Locust | < 1% |
| CPU %, RAM | `monitor.py` (`docker stats`, ~2 с) | CPU backend не впирається в стелю ядра event loop |

Точка перелому — кількість VUsers/RPS, при якій p95 різко зростає (>3× базового), RPS перестає
рости лінійно (< 80% від лінійного) або помилки перевищують 1%.

## 7. Обмеження

- Генератор і сервіс на одній машині (Docker Desktop VM: 8 CPU, ~1.8 ГБ RAM) — конкуренція за CPU.
- БД не очищується між прогонами (таблиці ростуть) — для початкового тесту прийнятно.
- `docker stats --no-stream` дає ~1 вибірку за 2 с.
